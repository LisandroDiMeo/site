# Deployment

## Modes

The site supports two deployment modes controlled by environment variables:

| | Local | Cloud (Cloudflare Pages) |
|---|---|---|
| Writing | External NAS (`VITE_EXTERNAL_WRITING_URL`) | External NAS (`VITE_EXTERNAL_WRITING_URL`) |
| Photos | Filesystem or external NAS | External NAS only |
| Config file | `.env` | `.env.production` |
| Build command | `npm run build:local` | `npm run build:production` |

## Environment Variables

### Local (`.env`)

```
VITE_APP_TITLE=Lisandro's Site
VITE_DEPLOYMENT_TYPE=local
VITE_PHOTOS_MODE=filesystem
VITE_LOCAL_PHOTOS_PATH=/assets/photos
VITE_EXTERNAL_PHOTOS_URL=https://sarusage.myasustor.com/photos
VITE_EXTERNAL_WRITING_URL=https://sarusage.myasustor.com/writing
```

### Production (`.env.production`)

```
VITE_APP_TITLE=Lisandro's Site
VITE_DEPLOYMENT_TYPE=cloud
VITE_PHOTOS_MODE=static
VITE_LOCAL_PHOTOS_PATH=/assets/photos
VITE_BASE_URL=/
VITE_EXTERNAL_PHOTOS_URL=https://sarusage.myasustor.com/photos
VITE_EXTERNAL_WRITING_URL=https://sarusage.myasustor.com/writing
```

In cloud mode photos are served from the external NAS URL.

## Writing (NAS)

Articles live in the Obsidian vault and are published to the NAS by `sync-writing.py`; the site reads them at runtime, so adding a note never requires a deploy.

```
python sync-writing.py --user <user> --password <pass>           # upload changed .md + write writing-index.json
python sync-writing.py --dry-run                                  # list what would be synced (no connection)
python sync-writing.py --user <user> --password <pass> --prune    # also delete remote .md removed from the vault
```

- Defaults: vault `~/Documents/Lecturas/lecturas`, remote `/volume1/Web/writing`, host `192.168.1.80`. Folders excluded by default are listed in `DEFAULT_EXCLUDES` in the script (override with repeated `--exclude`).
- Only `.md` files are uploaded. Notes with `draft: true` in the front-matter are skipped.
- `writing-index.json` is written next to the articles on the NAS (never to the repo). It has the same recursive shape as `photo-index.json` (`children`, `subdirs`, `file_details`), where each `file_details` entry carries `path`, `title`, `date`, `category`, `tags`, `note`.
- The site fetches `<VITE_EXTERNAL_WRITING_URL>/writing-index.json` and each article's `.md`, so the NAS must send `Access-Control-Allow-Origin` for the site's origin. Check with:
  `curl -sI -H "Origin: https://<site-domain>" https://sarusage.myasustor.com/writing/writing-index.json | grep -i access-control`

## Cloudflare Pages

Deployed as a Worker with static assets (Workers Builds). Build command: `npm run build:production`; deploy command: `npx wrangler versions upload`.

- `wrangler.jsonc` — tells wrangler to upload `./dist`. The `name` must match the Worker name in the Cloudflare dashboard. Without this file the deploy step fails with "Missing entry-point to Worker script or to assets directory".
- `not_found_handling: single-page-application` serves `index.html` for unknown routes (replaces the old `_redirects` rule, which Workers assets reject as an infinite loop).
- `public/_headers` — HTTP header rules

## Photo Index Generation

The photo gallery relies on `photo-index.json`, generated by a Python script that indexes photos from a NAS via SSH/SFTP and publishes it next to the photos (`/volume1/Web/photos/photo-index.json`). The site fetches it from `<VITE_EXTERNAL_PHOTOS_URL>/photo-index.json`, so new photos don't need a repo change or deploy; the NAS must send CORS headers for that file. `--local` also writes a copy to `public/photo-index.json`, used only when `VITE_EXTERNAL_PHOTOS_URL` is unset.

```bash
python generate-photo-directory.py \
  --user <ssh_user> \
  --password <ssh_password> \
  --host <nas_ip> \
  --remote-path <photo_directory>
```

- Connects via Paramiko SSH/SFTP
- Recursively scans for images (.jpg, .jpeg, .png, .gif, .webp, .bmp, .svg)
- Respects exclusions in `public/dont-show.json` (filtered files and directories)
- Collects file metadata: name, size, modified/created timestamps
- Outputs nested JSON with paths, files, file details, subdirectories, and photo counts
- Skips `_derived/` (and any `_`-prefixed folder) and macOS `._*` files

## Photo Thumbnails (NAS cron)

Originals are ~11 MB JPGs, far too heavy for the grid. `nas/generate-thumbnails.py` runs **on the NAS** (Asustor AS1102TL, aarch64, App Central Python 3.12 + `pip install --user pillow`) and mirrors the library as WebP:

| Variant | Path | Long side | Typical size | Used by |
|---|---|---|---|---|
| `thumb` | `/volume1/Web/photos/_derived/thumb/<path>.webp` | 480px | ~15 KB | `PhotoTile`, `PhotoAlbumCard` |
| `medium` | `/volume1/Web/photos/_derived/medium/<path>.webp` | 2048px | ~150 KB | `PhotoViewer` |

- Incremental: rebuilds a variant only when missing or older than the original; deletes variants whose original is gone; atomic writes; a lock prevents overlapping runs. ~2.5 s/photo on the NAS (a full rebuild of ~4.4k photos takes ~3 h).
- `--index` also rewrites `photo-index.json` from the local filesystem (same format as `generate-photo-directory.py`), only when its content changed, so with the cron in place uploading photos is enough to publish them.
- Exclusions come from `dont-show.json` **next to the script on the NAS** — re-copy `public/dont-show.json` after editing it.
- The site requests variants via `config.getPhotoVariantUrl()` with `?v=<modified>`, and falls back to the original (client-side downscaled) when a variant doesn't exist yet.

Install / update (from the Mac; copy each file separately):

```bash
scp nas/generate-thumbnails.py <user>@<nas_ip>:scripts/
scp public/dont-show.json <user>@<nas_ip>:scripts/
```

On the NAS:

```bash
python3 ~/scripts/generate-thumbnails.py --root /volume1/Web/photos --only RicohSOC/2026/July --dry-run   # preview
crontab -e   # add:
# 15 * * * * nice -n 19 python3 /volume1/home/<user>/scripts/generate-thumbnails.py --root /volume1/Web/photos --index >> /volume1/home/<user>/scripts/thumbs.log 2>&1
```

### NAS web server (nginx)

Photos are served by the App Central **Nginx 1.18** app (`/usr/local/AppCentral/nginx-1.18.0/data/conf/`). Its `sites-available/*.conf` are regenerated by the app, so customizations live in `conf.d/*.conf` (included inside both the :80 and :443 `server` blocks):

- `photos-derived.conf` — `location ^~ /photos/_derived/`: CORS + `Cache-Control: public, max-age=31536000, immutable` (no `always`, so 404s for not-yet-generated variants are not cached).
- `cors-images.conf` — CORS for image extensions + `Cache-Control: public, max-age=604800` on originals.
- `cors-photos-index.conf` — CORS, `no-cache`, and gzip for `photo-index.json` (1.2 MB → ~115 KB).
- `cors-writing.conf` — CORS + `no-cache` for `/writing/`.

Remember a `location` with its own `add_header` does not inherit parent `add_header`s — repeat CORS in each. Validate and reload with:

```bash
N=/usr/local/AppCentral/nginx-1.18.0/data/sbin/nginx; C=/usr/local/AppCentral/nginx-1.18.0/data/conf/nginx.conf
sudo $N -t -c $C && sudo $N -s reload -c $C
```
